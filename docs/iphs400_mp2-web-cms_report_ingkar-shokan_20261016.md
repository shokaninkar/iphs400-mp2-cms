## What I built and what I decided

I built a small CMS for **inkadmissions**, my admissions-consulting project for Central Asian students looking at US colleges with full financial aid. I kept the editing interface local (FastAPI, Jinja2 and SQLite) and generated a separate static site for GitHub Pages. I did not want the public site to expose the administrative login or editing routes.

During `/grill-with-docs` on September 29, Claude recommended that Posts should be **client-results spotlights**. I chose recurring **admissions tips** instead, because I want the site to explain the application process, not just display outcomes. We named them **Notes** to distinguish them from the evergreen Guide. I also made the call to keep English/Russian bilingual publishing out of this MVP and to run the new CMS alongside the existing website rather than replace it. A narrower first version made it easier to check whether the draft-to-publish workflow actually worked. I kept Pages administrator-only and restricted the editor to drafting her own Notes; I still review anything before it becomes public.

Looking back, the next change I want is a way for Aigerim to request publication and receive feedback. I would keep the final approval with the administrator, but the current draft-only rule needs a clearer handoff. English-only kept the first build manageable, although it leaves the bilingual audience only partly served. Russian Notes remain a possible later extension. The fictional name itself matters less than being clear that Aigerim is a persona, not an employee I interviewed.

## Where AI went wrong and what caught it

The T04 review on October 6 found that a **duplicate slug caused a 500 server error** instead of a useful validation message (review finding S7, later tracked in issue #9 for both Notes and Pages). The code assumed titles would always create unique URLs, which real editors cannot be expected to guarantee. It was caught in `/code-review`, then handled as a separate follow-up issue rather than ignored. Another very concrete mistake was in T04 public-page links: links that looked fine on the home page broke one folder down, under `/pages/`, because the stylesheet and home links resolved inside that folder (T04 review finding S1). This made me pay attention to actual deployment paths, not just green tests.

During T07, generated seed copy also claimed **“Every US college”** and **“many of them”** beyond what the existing site supported. Those statements were toned down against the source material. That is a different kind of AI drift: plausible marketing language is still a factual change, and it should not go live just because it sounds good.

I mostly relied on review for the code problems above; I should not present them as bugs I personally diagnosed. A problem I did notice myself was that nothing seemed to be happening after my October 16 prompt. In sessions 05 and 06 I put the task after `/clear` on the same line and then asked “are you working on it?” or “working?” Claude explained that `/clear` had ignored the rest. That was a mistake in how I started the task, not a coding bug. It taught me to check that work has actually started instead of assuming that typing a command is evidence it ran. The misleading Pages permission test was fixed by Claude in the T05 session, using a real CSRF token; I did not write that fix myself.
