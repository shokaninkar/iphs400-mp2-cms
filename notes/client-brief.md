# Client brief — inkadmissions

**Client and operator.** I run inkadmissions, an admissions-consulting project aimed at students in Central Asia applying to US colleges with full financial aid. Today I use Claude to help edit the code for the existing static, bilingual site. Even a short new tip means changing the site files and going through deployment. I want to write the tip in a form instead of turning every content update into another coding session. The editor role in this assignment is **Aigerim, a fictional assistant persona**, based in Almaty and named during the September 29 grill; she is not presented as a verified real employee. The workflow assumes she can work in a simple browser form, not maintain the codebase.

**Readers and their questions.** The site is aimed at students and families in Central Asia, including Kazakhstan. The questions the Notes should answer are concrete: “Can an international student get full aid?”, “What is the difference between need-blind and need-aware?”, and “What should I do next?” These are the content priorities for this brief; I have not measured which question appears most often in DMs. The existing Ink's Diary Telegram audience is one way students might find the site, but this CMS is for **inkadmissions**, not the Telegram brand. Readers should be able to open **The Guide**, learn who is behind the project on **My Story**, and find next steps on **Work With Me**.

**What's painful now.** The current code-and-deploy workflow depends on me and Claude. The assistant persona cannot independently add a tip through a simple form on the existing site. I have not timed a small update, so I cannot honestly give a minutes-per-update figure. Separating time-sensitive Notes from permanent Pages is important: a dated tip should not require touching the main navigation. It is also easy for polished copy to overstate facts; in T07 two overly broad claims about US colleges had to be softened to match the source.

**What “better” means.** I can draft, preview and publish a Note without editing HTML, and a reader sees it only after I approve it. An editor can prepare her own Notes but cannot publish, change the three navigation Pages or manage accounts. Published links need to work under the GitHub Pages project subpath, including on a phone.

**What must not happen.** A draft must never leak onto the public website. The admin console, logins and database must not be deployed with the static export. An editor should not be able to escalate permissions by typing a URL directly. Duplicate slugs should not crash the app, and source-supported claims about aid and admissions should not be embellished by AI.

**Scope for MP2.** English-only CMS, running in parallel to the existing website. EN/RU publishing, categories and tags, and automatic migration to the live site are future questions rather than promises.
